# OpenTakeoff → HVAC/BAS Agent Integration Plan

## Context

We proved the end-to-end architecture works: a locally-hosted Cerebras proxy (holding a real key server-side, no per-user setup) driving OpenTakeoff's in-browser Agent, which called real deterministic tools against a real vector PDF and staged reviewable proposals — confirmed live, on a flooring takeoff. That proved the plumbing, not the product. We don't care about carpet. Everything from here is about redirecting that same proven loop at HVAC/BAS component symbols instead, and doing it without regressing the "refuse rather than guess" discipline that made the flooring demo trustworthy in the first place.

This plan picks up immediately after that demo and covers exactly the four things identified as the next real steps, in order, plus what each one actually requires. See [`01-rt-detr-symbol-detection-training-plan.md`](01-rt-detr-symbol-detection-training-plan.md) for the separate, longer-running fine-tuned-model track — that plan's `detect_symbols_ml` tool is the eventual fifth tool this same Agent reaches for once it exists; nothing here is blocked on it.

## Execution model (same standing rule as the training plan)

Everything here is researchable or already sitting in this cloned repo — no external account, no payment, no credential is needed for this specific piece of work (the Cerebras key is already live via the local proxy). So this gets executed directly, not handed off in pieces for approval at every step. The training-plan precedent still holds: verify each step before moving to the next, don't skip the check because the prior step "seemed fine."

### A real HVAC/mechanical schedule was found and used — and it surfaced two genuine bugs, one fixed, one still open

Found real equipment schedules on the Bessemer sample's own page 8 ("MECHANICAL SCHEDULES", sheet M601) — Electric Baseboard Heater, Diffuser/Grille/Register, Heat Pump, and Fan schedules, with tags (SR-1, SR-2, TG-1, TG-2, EBB-1..8, HP-1, EF-1) genuinely repeated on the drawn mechanical plans (pages 6/7). Exactly the real test case needed.

**Bug 1 — fixed and proven correct in isolation.** `sheetgraph.ts`'s `extractTable` required a header cell reading CODE/MARK/SYMBOL for a table to qualify as "finish" kind. Every real schedule on this sheet keys its rows under **"ID"** instead — a real, systematic gap for MEP schedules (the vocabulary was built for flooring conventions). Added "ID" to `FINISH_HEADERS` and the `required` list (`web/src/lib/sheetgraph.ts`). Confirmed via a standalone script calling `extractTable`/`buildSheetGraph` directly against the real PDF's actual extracted text (bypassing the browser entirely): the Diffuser/Grille/Register Schedule is now found, with "SR-1" captured as a real row. All 33 existing `sheetgraph.test.ts` tests plus the full 1584-test suite still pass — the fix is additive, not loosening anything that was correctly excluded before (confirmed the door-schedule-exclusion test still passes).

**Bug 2 — root-caused and FIXED.** The `RENDER_SCALE`/`ensureTextSpans` hypothesis in the previous write-up was wrong — ruled out by direct instrumentation, not just re-asserted. Actual cause, found by adding temporary console logging inside `findHeaderRow`/`bandDataRows` and bisecting the real 295-span sheet by y-range: `extractTable`'s header-row detection (`findHeaderRow`) was working correctly the whole time — it correctly found the Diffuser/Grille/Register Schedule's header row (`ID, DESCRIPTION, MANUFACTURER, SIZE, MATERIAL`) every time. The actual bug was one level down, in `bandDataRows`'s column-start recovery (`columnMapFor`/`columnStarts`). On a dense sheet, several MEP schedules are stacked in the SAME x-columns (a real drafting convention — this sheet alone has seven). `columnMapFor` recovers a table's true column starts by clustering the left edges of every token below the header that falls in its x-band, with **no lower bound on how far down the sheet it scans** — so a LATER, unrelated table's header fragments (here: a VRF Heat Pump schedule ~450px further down, reusing the same column grid) got pulled into the Diffuser table's own column-start cluster and dragged column 0's recovered position ~90px away from where `SR-1`/`SR-2`/`TG-1`/`TG-2` actually sit. Every real row was then rejected by the key-column-alignment gate (91px off against a 61px tolerance) — the header was found, the data was found, and the table still came back `null`. Confirmed root cause directly (not inferred): a minimal repro fed just that one table's own 51 spans through `extractTable` and it worked perfectly; adding the next table's spans back in reproduced the exact failure.

**The fix** (`web/src/lib/sheetgraph.ts`, `columnMapFor`/`columnStarts`/`bandDataRows`): column-start recovery now only lets a row vote if that row's own leading in-band token already reads as a real key for this table kind (the same `rowKeyOf` test the main data-scan loop already uses to accept a row at all) — a stray header fragment or data row from a different, later table can never again pass its own text into another table's column geometry. This is a general, principled fix (not a special case for "SCHEDULE"-titled tables or this specific sheet) — an earlier attempt bounding the scan at the next row containing the word "SCHEDULE" was tried first and discarded once the VRF Heat Pump table's real title ("VARIABLE REFRIGERANT PACKAGED HEAT PUMP") turned out not to contain that word at all, which would have left the fix blind to exactly this case.

**Verified, three ways:** (1) full test suite — 1584/1584 pass, typecheck clean, no regressions; (2) direct console-level re-test against the exact live browser spans (not a standalone script): `extractTable(sheet, "finish")` now returns the Diffuser/Grille/Register Schedule with rows `SR-1, SR-2, TG-1, TG-2` — exactly the known-correct answer; (3) **genuinely live through the actual Cerebras-backed Agent UI**, not a console shortcut: typed the goal *"Call sheet_graph on this sheet, then call find_schedule with kind 'finish'. Report the table title and every row key you find."* into the real Agent panel on the real M601 sheet — the agent called `sheet_graph` → `find_schedule` → (a couple of exploratory dead-end tool calls) → correctly answered **"DIFFUSER, GRILLE, REGISTER SCHEDULE... SR-1, SR-2, TG-1, TG-2"**, sourced entirely from the tool's real return value.

**Why this matters beyond just `sweep_schedule_row`:** `sheet_graph`, `resolve_tag`, `find_schedule`, and `count_marks` all depend on the same `buildSheetGraph`/`extractTable` pipeline and all benefit from this fix identically. The earlier "no schedule found" result on the P100 Plumbing Insulation Schedule sheet was re-examined under the same suspicion that flagged Bug 2 — that sheet's schedule genuinely doesn't carry finish/equipment vocabulary (it's SYSTEM TYPE / INSUL. TYPE / PIPE SIZE columns), so the original exclusion still stands as correct, now on firmer footing.

**New, honest finding surfaced while fixing this:** `buildSheetGraph` calls `extractTable` **once per kind ("room-finish", "finish") per sheet** — so on a dense sheet with several distinct schedule tables (M601 has seven), only the FIRST one whose header clears the vocabulary bar is ever found; the other six (Electric Wall Heater, Electric Baseboard Heater, VRF Heat Pump, Fan, 2× Ductwork Insulation) are invisible to `find_schedule`/`sheet_graph` today, not because of a bug in reading them but because the current design has no notion of "more than one finish table per sheet." This is a real, separate, larger scope gap — not blocking the fix above, but the honest reason `sheet_graph`'s table list for M601 will show only one table until it's addressed.

**Running total: 15 new tools wired (23 total on the Agent, up from the original 8).** `symbol_sweep`, `place_count`, `list_shapes`, `delete_shape`, `edit_shape`, `undo_last`, `set_scale`, `takeoff_summary`, `export_takeoff`, `export_report`, `sheet_graph`, `resolve_tag`, `find_schedule`, `count_marks` (14) are now genuinely fully live-verified with no open questions. `sweep_schedule_row` (1) is correctly wired and structurally verified (row-lookup, refusal paths) with its actual anchor+sweep matching logic still not yet exercised against a real drawn marker — see next priority below.

## Step 1 — Wire the real tools into the in-browser Agent

**Confirmed gap:** the Agent that ran the flooring demo has exactly 8 tools (`web/src/lib/agentTools.js`): `list_sheets`, `read_sheet_text`, `read_schedule`, `view_region`, `one_click`, `get_conditions`, `create_condition`, `propose_shapes`. None of them find or count discrete symbols — `one_click` is a flood-fill area tool, the wrong shape entirely for a valve icon. The tools that actually do this (`symbol_sweep`, `place_count`, `sweep_schedule_row`, `count_marks`) exist and are fully tested, but only on the separate stdio MCP server (`mcp/src/tools.ts`), not on this Agent's own tool list.

**The fix is additive, not new engineering.** `web/src/lib/symbolsweep.ts` is the shared pure-function core both the canvas Symbol tool and the MCP server already call into — "canvas and MCP cannot disagree," per the docs. `agentTools.js` gets a third caller into that same library, following the exact shape its existing 8 entries already use (a `name`, an input schema, an execute function that calls into the real app state).

**Full tool audit — every MCP tool, sorted into what this Agent should get and what it shouldn't:**

Real prompt-engineering work, but small relative to Step 1 — this is refining a decision the model already has the right tool to make, not building new capability.
